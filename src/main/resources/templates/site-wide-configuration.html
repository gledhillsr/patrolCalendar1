Create the self-made tables everywhere

Runs CREATE TABLE IF NOT EXISTS for menubuttons, shifttemplatepatrollers and <resort>_password_reset_tokens against every resort in PatrolData.resortMap. Safe to run more than once - a resort that already has a table is left as it is.

Once every resort reports ok, that table's create-on-first-use call can come out of its read and write paths. menubuttons and shifttemplatepatrollers have been through this; password_reset_tokens still creates itself on demand until this has run everywhere.

Both are listed even though only one is being migrated at a time: a resort added to the map later needs all of them, and this is the only place that can give it one.

Give every resort its calendar-sync settings

Adds a timeZone column to each resort's settings and fills it in with the zone worked out from that resort's name and website. A resort that already has one — because a director set it on Web Site Preferences — is left alone, so this never overrides somebody's answer.

It also adds the calendarSyncEnabled switch, created switched off. Personal calendar sync is a resort's own decision, made by its director on Web Site Preferences — turning it on for 44 resorts from a button pressed here would be found by a patroller, not by you.

Run this before deploying a jar that expects those columns. A save names every column it writes, so a resort missing one would lose a director's whole preferences change, not merely the new setting — the code guards against it, but the guard is a safety net rather than the plan.

Safe to press again. A resort already done reports already set.

The zone is what lets a shift be described correctly to anything outside this site — a patroller's own calendar above all, where “8:00” means nothing without it.

Add the shift Label column, and sort the old Start values into it

A shift row now carries a Label - what the calendar shows, such as TL, dir or mentee - separately from its Start Time. The Start field was free text for twenty years, so most resorts have both real times and job names sitting in the one column.

This gives every resort the Label column, then sorts what is already there: a Start value that reads as a time stays, rewritten in one canonical form (0800, 8am and 8:00 all become 8:00); a Start value that is not a time was always a label, so it moves to the Label and the Start is emptied. End times are left exactly as they are.

Safe to press again. A resort that has already been done reports nothing to do and nothing is written. It judges by the data rather than by whether the column exists, so a resort left half-done by an interrupted run gets finished rather than skipped.

This rewrites rows in two tables, in every resort, and there is no undo. Take a database backup of shiftdefinitions and assignments before the first run.

Until a resort has been through this, the shift editors and the daily reminder cannot read its shifts - they expect the Label column.

Tidy shift template start and end times

Finishes what the Label job started, on the templates only. Three things were left behind, and every one of them the computer can settle by itself:

  • A time sitting in the Label with no Start beside it. The old rule insisted on the m of the meridiem, so 4:00P and 8:00 a were read as labels and moved out of the Start column, which was then emptied. Those shifts have no start time at all until this fills one in — 4:00P gives a Start of 16:00. The Label itself is left exactly as it is, so the calendar goes on showing what it shows today; only the missing Start is added.
    It also reads a time written into one end of a caption — Vol 10:00AM and 8:30 Paid both give a Start, and keep their caption. A bare number is never read as a time, so Train 2 and Avy 1 stay as they are: those are course and team numbers.
  • A Start that is a time but not written canonically.
  • An End that is a time but not written canonically - 1600, 4:30pm, 2100. End was never migrated, so this is most of the work.

What it cannot read it leaves alone: Close, end time, 5:30-9 and a blank End stay exactly as they are, and are listed for a director on that resort's Edit Shift Templates page instead.

Templates only, deliberately. The scheduled days carry the same faults across twenty years of history, and rewriting a shift somebody worked in 2019 helps nobody. Templates are what build the seasons ahead. Safe to run more than once - a row already in canonical form is not written, and a second press reports nothing to do.

Remove shift templates with no event name

A template row's position lives in a _<n> suffix on its name, and the template editor used to accept a blank name - writing rows called _0 that belong to no template and show as a blank entry in its dropdown. Nothing can create one any more; this clears up what was left behind.

Find first. It only reports, so it is safe to press.
